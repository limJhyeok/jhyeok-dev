> **TL;DR**
>
> **1. 도구는 하드웨어가 먼저 정합니다.**
> - **NVIDIA GPU**: `TensorRT`
> - **Intel**: `OpenVINO`
> - **멀티 벤더 및 이기종 환경**: `ONNX Runtime`
> - **거대 언어 모델(LLM) 서빙**: `vLLM`·`SGLang`·`TensorRT-LLM` 등 전용 생태계
>
> **2. PyTorch 안에서 할 수 있는 최적화는 세 가지입니다.**
> - `.half()`: 모델 전체를 **FP16**으로 전환
> - `torch.autocast`: 연산별로 FP16과 FP32를 자동으로 섞어 실행(**혼합 정밀도**)
> - `torch.compile`: 연산 **그래프를 캡처**해 kernel을 융합(kernel fusion)
>
> **3. TensorRT는 빌드할 때 kernel을 직접 실행해 속도를 잽니다.**
> 모든 shape과 GPU에서 가장 빠른 kernel은 없으므로, 실제 GPU에서 레이어마다 후보 kernel(tactic)을 돌려 보고 가장 빠른 조합을 engine 파일에 고정합니다.
> 그래서 engine은 기본적으로 빌드한 **GPU 아키텍처와 TensorRT 버전**에서만 동작합니다.
>
> **4. T4 + ResNet-18(batch 8)에서 PyTorch FP32 대비 속도**
> - **FP16으로 낮췄을 때**
>     - `.half()` 단독: **2.3배**
>     - `torch.compile` + FP16: **3.5배**
>     - TensorRT + FP16: **5.1배**
> - **FP32를 유지했을 때**
>     - `torch.compile`: **1.02배**
>     - TensorRT: **1.3배**

## Intro

이전 글까지는 CCTV 영상에서 얼굴을 찾고, 등록하고, 추적하고, 디코딩하는 과정을 다뤘습니다.
이때 쓴 모델은 YOLO 계열 검출기나 InsightFace의 ArcFace처럼 공개된 PyTorch·ONNX 모델을 그대로 불러온 것입니다.
데모나 카메라 한두 대 수준이라면 PyTorch·ONNX 모델을 그대로 써도 충분합니다.

문제는 규모가 커질 때 생깁니다.
동시 요청이 늘거나, 처리할 이미지 해상도와 영상 길이가 커지면 **모델 추론에서 먼저 병목**이 될 가능성이 큽니다.
프레임마다 Detector를 실행하고, 검출된 얼굴마다 임베딩 모델을 실행하기 때문에 모델 호출 횟수가 영상 길이와 얼굴 수에 비례해 늘어납니다.

병목을 줄이는 방법은 여러 가지가 있을 수 있습니다.
GPU 서버를 더 늘리거나, 프레임을 건너뛰거나, batch로 묶거나, 더 작은 모델로 바꾸거나, 서빙 구조를 바꿀 수 있습니다.
이 시리즈에서 하나씩 실험해 볼 텐데, 가장 먼저 해볼 것은 **모델을 추론에 적합한 형태로 바꾸는 것**입니다.

이유는 비용 대비 효과입니다.
모델 구조나 학습은 건드리지 않고, 파이프라인 로직도 그대로 둔 채 모델의 정밀도나 실행 방식만 바꾸면 됩니다.
변경은 코드 한 줄에서 수십 줄 수준인데, 정확도는 거의 그대로이면서 latency는 수 배 줄어들 수 있습니다.

### 왜 처음부터 최적화된 모델로 배포하지 않을까

그렇다면 왜 모델 저장소들은 처음부터 최적화된 형태가 아니라 PyTorch(`.pt`)나 ONNX(`.onnx`)로 모델을 배포할까요?

최적화된 추론 모델은 **실행할 환경에 따라 달라지기 때문**입니다.
NVIDIA GPU용 추론 엔진인 TensorRT를 예로 들면, 같은 모델이라도 GPU 아키텍처(T4인지 A100인지), TensorRT 버전, 입력 shape(batch 크기, 해상도), 정밀도(FP32·FP16·INT8)에 따라 가장 빠른 결과물이 다릅니다.
그리고 그 결과물은 기본적으로 아키텍처가 다른 GPU에서는 실행조차 되지 않습니다.
배포자 입장에서 모든 조합을 미리 만들어 둘 수는 없으니, 모델 제작자는 어디서나 쓸 수 있는 PyTorch·ONNX를 배포하고, 최적화는 실제로 돌릴 환경에서 사용자가 합니다.

또 하나의 이유는 **수정 가능성**입니다.
모델을 받은 사람이 추론만 하는 것은 아닙니다.
자기 데이터로 fine-tuning하거나, 실험을 위해 loss·layer 같은 내부 알고리즘을 바꿔 보기도 합니다.

- **PyTorch**: 모델이 코드 그대로입니다. 학습도, 알고리즘 수정도 자유롭습니다.
- **ONNX**: 표준 연산자로 이루어진 그래프입니다. 노드를 교체하거나 추가하는 그래프 수준의
  수정은 가능하지만, 알고리즘을 바꾸려면 그래프를 직접 고쳐야 해서 번거롭습니다.
  학습용 포맷도 아닙니다. PyTorch에서 export하는 단계에서 이미 데이터에 따라 갈라지는
  분기처럼 표현하기 어려운 부분은 사라지거나 고정됩니다.
- **TensorRT engine**: 빌드 과정에서 레이어가 합쳐지고(Conv + BN + ReLU → kernel 하나),
  BN은 가중치에 흡수되고, GPU별 kernel이 고정됩니다. 원래 구조가 남아 있지 않으므로
  engine을 직접 고치는 것은 사실상 불가능하고, ONNX나 PyTorch로 돌아가 고친 뒤 다시
  빌드해야 합니다. (refit 옵션으로 빌드한 engine은 가중치 교체는 가능하지만 구조는 바꿀 수 없습니다.)

정리하면 `PyTorch` → `ONNX` → `TensorRT engine`으로 갈수록 빨라지는 대신 수정할 수 있는 범위가 줄어듭니다.
그래서 배포는 수정 가능한 형태로 하고, 추론에 최적화된 형태로의 변환은 마지막 단계에서 합니다.

### 이 글에서 다루는 것

추론 최적화 기술은 **어떤 하드웨어에서, 어떤 모델을, 얼마나 빠르게** 돌려야 하는지에 따라 선택이 달라집니다. 
이 글은 먼저 그 선택지를 정리하고, NVIDIA GPU에서 쓸 수 있는 네 가지 방법을 가벼운 것부터 차례로 살펴봅니다.

- **다루는 것**
    - 추론 엔진 선택 기준
    - PyTorch 안에서 하는 최적화: FP16 변환(`.half()`), `torch.autocast`, `torch.compile`
    - TensorRT: 빌드가 필요한 이유, 객체 구조, PyTorch → ONNX → engine 빌드와 추론
    - 네 방법의 정확도·latency 비교
- **다루지 않는 것**: INT8 calibration, LLM 추론 최적화, Triton Inference Server 배포 등

> **제외한 이유**
>
> - **INT8 calibration**: 대표적인 양자화 기법이지만, 대표 데이터셋으로 calibration하는 과정이 따로 필요합니다. FP16보다 정보 손실이 커서 정확도나 출력이 눈에 띄게 달라질 수 있으므로, 처음 시도할 손쉬운 최적화로는 맞지 않습니다.
> - **LLM 추론 최적화**: LLM은 KV cache, PagedAttention, continuous batching 같은 전용 최적화가 필수라서, 일반 모델용 TensorRT가 아니라 vLLM·TensorRT-LLM 같은 별도 생태계에서 다룹니다.
> - **Triton Inference Server 배포**: Triton은 모델의 연산이나 가중치를 최적화하는 도구가 아니라, dynamic batching, 멀티 모델 관리, 여러 백엔드 라우팅을 맡는 서빙 인프라입니다.

## 1. 추론 최적화 도구 고르기

### 1.1 배포 하드웨어 기준

가장 먼저 추론이 실행될 장치(하드웨어)의 제조사가 추론 엔진을 결정합니다.

| 하드웨어 | 추론 엔진 | 이유 |
| --- | --- | --- |
| **NVIDIA GPU** (서버, RTX, Jetson) | **TensorRT** | CUDA 코어와 Tensor Core에 맞춘 kernel을 골라 써서 NVIDIA GPU에서 대체로 가장 빠릅니다. |
| **Intel CPU / 내장·외장 GPU / NPU** | **OpenVINO** | NVIDIA GPU가 없는 Intel 장비에서 효율적으로 추론합니다. |
| **여러 벤더 혼용** | **ONNX Runtime** | 하드웨어 종속성이 적고, Execution Provider만 바꿔 TensorRT나 OpenVINO를 백엔드로 붙일 수 있습니다. |
| **모바일 / 엣지** | **LiteRT(구 TFLite), Core ML** | Android(LiteRT)와 Apple 기기(Core ML)의 모바일 NPU를 쓰려면 사실상 표준입니다. |

### 1.2 모델 유형 기준

일반 딥러닝 모델과 LLM은 최적화 생태계가 따로 발전하고 있습니다.

- **컴퓨터 비전 / 일반 딥러닝** (YOLO, ResNet, ArcFace, BERT 등)
    - 그래프 구조가 비교적 정적이어서 **TensorRT**나 **OpenVINO**로 미리 컴파일해 두는 방식이 잘 맞습니다. 이 시리즈의 얼굴 검출·인식 모델이 여기에 속합니다.
- **LLM / VLM**
    - **vLLM / SGLang**: 여러 사용자의 요청을 동시에 처리해 throughput을 높이는 서빙 엔진입니다. PagedAttention 같은 KV cache 메모리 관리가 핵심입니다.
    - **TensorRT-LLM**: NVIDIA GPU의 성능을 최대한 끌어내야 할 때 씁니다.
    - **llama.cpp / Ollama**: 개인 PC, Apple Silicon, CPU 환경에서 GGUF로 양자화한 모델을 가볍게 돌릴 때 씁니다.

### 1.3 모델 경량화 기법

엔진과 별개로 모델 자체를 가볍게 만드는 기법도 함께 사용할 수 있습니다.

- **양자화(Quantization)**: 가중치와 연산의 정밀도를 FP32 → FP16·INT8·INT4로 낮춰 메모리와 연산량을 줄입니다. 정확도 손실이 거의 없는 **FP16**을 기본으로 고려하고, 정확도를 어느 정도 내주더라도 더 빨라야 하면 **INT8**(비전 모델)이나 **AWQ / GPTQ 4-bit**(LLM)를 검토합니다.
- **지식 증류(Knowledge Distillation)**: 큰 모델(teacher)의 출력을 작은 모델(student)이 따라 하도록 학습시켜 구조 자체를 작게 만듭니다.
- **프루닝(Pruning)**: 중요도가 낮은 가중치나 채널을 제거해 연산량을 줄입니다.

### 1.4 실무 흐름

1. **기본 경량화**: 정확도 하락이 작은 **FP16**을 먼저 적용해 봅니다.
2. **PyTorch 안에서 최적화**: PyTorch 환경을 유지해야 한다면 `torch.compile`을 더합니다.
3. **엔진 적용**: 더 빨라야 하면 모델을 **ONNX**로 export하고, NVIDIA GPU면 **TensorRT**, Intel CPU나 엣지 PC면 **OpenVINO**로 변환합니다.
4. **서빙 인프라**: 여러 모델을 동시에 띄우고 트래픽이 많다면 **Triton Inference Server** 같은 추론 서버로 dynamic batching을 적용합니다.

이 글은 1~3단계를 NVIDIA GPU 기준으로 다룹니다.

## 2. PyTorch 안에서 하는 최적화

모델을 다른 포맷으로 바꾸지 않고, PyTorch 코드 안에서 바로 적용할 수 있는 방법부터 봅니다.
셋 다 학습 코드나 파이프라인 구조를 바꿀 필요가 없습니다.

### 2.1 FP16 변환: `.half()`

딥러닝 모델의 가중치와 연산은 기본적으로 FP32(32bit 부동소수점)입니다.
`.half()`는 모델의 모든 파라미터와 버퍼를 FP16(16bit)으로 바꿉니다.

```python
model_fp16 = model.half()          # 가중치 FP32 → FP16 (in-place라 model 자신도 FP16이 된다)
x_fp16 = x.half()                  # 입력도 FP16으로 맞춰야 한다

with torch.inference_mode():
    y = model_fp16(x_fp16)         # 출력도 FP16
```

빨라지는 이유는 두 가지입니다.

- **Tensor Core**: 
    - NVIDIA GPU의 Tensor Core는 행렬곱 전용 연산 장치입니다. 
    - Volta(V100) 이후 GPU는 FP16 행렬곱을 Tensor Core로 처리하므로, 같은 Conv·Linear 연산이 CUDA 코어로 FP32를 계산할 때보다 몇 배 빠릅니다.
- **메모리 대역폭**: 
    - 값 하나가 4byte에서 2byte로 줄어 가중치와 activation을 읽고 쓰는 양이 절반이 됩니다. 
    - 모델 파일 크기와 GPU 메모리 사용량도 절반이 됩니다.

대신 표현할 수 있는 범위와 정밀도가 줄어듭니다.

| 형식 | 비트 구성 (부호·지수·가수) | 최대값 | 유효 자릿수(10진) |
| --- | --- | ---: | ---: |
| FP32 | 1 · 8 · 23 | 약 $3.4 \times 10^{38}$ | 약 7자리 |
| FP16 | 1 · 5 · 10 | 65504 | 약 3자리 |
| BF16 | 1 · 8 · 7 | 약 $3.4 \times 10^{38}$ | 약 2자리 |

추론에서는 대부분 문제가 없지만, 큰 값을 더해 가는 연산(합계, softmax의 지수 등)에서 65504를 넘으면 `inf`가 되고, 아주 작은 값은 0으로 사라질 수 있습니다.
BF16은 FP32와 지수부가 같아 overflow 걱정이 적지만, BF16 Tensor Core는 Ampere(A100, RTX 30xx) 이후에만 있습니다.
이 글의 실습 GPU인 T4(Turing)에서는 FP16을 씁니다.

주의할 점이 두 가지 있습니다.

- **입력 dtype도 맞춰야 합니다.** 모델만 `.half()`하고 FP32 입력을 넣으면 dtype이 맞지 않는다는 에러가 납니다. 전처리 마지막 단계에서 입력을 FP16으로 바꾸거나, 모델 앞에서 변환해 줍니다.
- **`.half()`는 모델을 그 자리에서 바꿉니다.** 반환값을 새 변수에 받아도 원래 `model`까지 FP16이 됩니다. FP32 모델을 남겨 두고 비교하려면 4.1처럼 `copy.deepcopy(model).half()`로 복사본을 바꿉니다.

### 2.2 혼합 정밀도: `torch.autocast`

`.half()`는 모든 연산을 FP16으로 돌립니다. `torch.autocast`는 **연산 종류마다** FP16과 FP32 중 하나를 골라 실행합니다(AMP, Automatic Mixed Precision).

```python
with torch.inference_mode(), torch.autocast("cuda", dtype=torch.float16):
    y = model(x)    # 모델·입력은 FP32 그대로
```

autocast 블록 안에서는 PyTorch가 연산을 호출할 때마다 정해진 규칙으로 dtype을 바꿉니다.

- **FP16으로 실행**: Conv, Linear, matmul처럼 Tensor Core의 이득이 크고 FP16으로도 정밀도가 충분한 연산
- **FP32로 실행**: softmax, log, 합계(sum), norm, loss처럼 값의 범위가 넓거나 오차가 누적되기 쉬운 연산

가중치는 FP32로 남아 있고, 연산 직전에 FP16 사본을 만들어 계산합니다.
그래서 `.half()`와 비교하면 다음 차이가 있습니다.

| | `.half()` | `torch.autocast` |
| --- | --- | --- |
| 가중치 저장 | FP16 | FP32 (메모리 절감 없음) |
| 연산 정밀도 | 전부 FP16 | 연산별로 FP16/FP32 |
| 입력 dtype | FP16으로 맞춰야 함 | FP32 그대로 |
| 수치 안정성 | overflow 위험을 직접 관리 | 위험한 연산은 자동으로 FP32 |
| 추가 비용 | 없음 | 호출마다 dtype 변환(cast) |
| 학습 | 권장하지 않음 | 표준 방법 (`GradScaler`와 함께) |

autocast는 원래 **학습**을 위해 만들어졌습니다. 학습에서는 가중치 업데이트를 FP32 가중치에 누적하고, FP16에서 0으로 사라지기 쉬운 작은 기울기는 loss를 키웠다가 되돌리는 `GradScaler`로 지킵니다.
추론에서는 기울기가 없으니 `GradScaler`가 필요 없고, 정확도 문제가 없다면 `.half()`가 cast 비용이 없는 만큼 조금 더 빠릅니다. 반대로 `.half()`로 바꿨더니 출력에 `inf`·`NaN`이 생기는 모델이라면 autocast가 안전한 선택입니다.

### 2.3 그래프 컴파일: `torch.compile`

PyTorch는 기본적으로 **eager 모드**로 실행됩니다. Python이 `forward()`를 한 줄씩 실행하면서 연산 하나마다 GPU kernel을 하나씩 띄웁니다.
이 방식은 디버깅이 쉽지만 두 가지 비용이 있습니다.

- **kernel launch 오버헤드**: 연산마다 Python → C++ → CUDA로 내려가 kernel을 띄웁니다. 연산 하나가 작을수록 실제 계산보다 띄우는 비용의 비중이 커집니다.
- **메모리 왕복**: `y = relu(x + b)`라면 덧셈 결과를 GPU 메모리에 썼다가 ReLU가 다시 읽습니다. 두 연산을 하나의 kernel로 합치면(fusion) 중간 결과를 메모리에 쓰지 않아도 됩니다.

`torch.compile`은 모델을 한 번 감싸기만 하면 이 두 비용을 줄입니다.

```python
model_compiled = torch.compile(model)   # 이 시점에는 아무 일도 일어나지 않는다

with torch.inference_mode():
    y = model_compiled(x)   # 첫 호출: 그래프 캡처 + 컴파일 (수십 초)
    y = model_compiled(x)   # 이후 호출: 컴파일된 kernel 실행
```

내부에서는 세 단계가 일어납니다.

1. **TorchDynamo**: Python 코드를 실행하면서 텐서 연산을 가로채 연산 그래프(FX graph)로 캡처합니다. 그래프로 표현할 수 없는 코드(print, 데이터에 따라 달라지는 분기 등)를 만나면 그래프를 끊고(graph break) 그 부분만 eager로 실행합니다.
2. **AOTAutograd**: 그래프를 더 작은 기본 연산으로 풀어 정리하고, 학습이라면 backward 그래프까지 미리 만듭니다.
3. **TorchInductor**: 그래프를 보고 이어진 연산을 합쳐, GPU에서는 **Triton** kernel 코드를 생성하고 컴파일합니다. 행렬곱·Conv는 cuBLAS·cuDNN 같은 라이브러리를 호출하고, 그 앞뒤의 elementwise 연산을 합친 kernel을 만듭니다.

알아 둘 점이 몇 가지 있습니다.

- **첫 호출이 느립니다.** 컴파일에 수십 초가 걸리므로 서버라면 기동 시 warmup 호출을 넣습니다.
- **입력 shape이 바뀌면 다시 컴파일합니다.** 두 번째로 다른 shape이 들어오면 shape을 변수로 둔 dynamic 그래프로 한 번 더 컴파일합니다. batch 크기가 계속 바뀌는 서비스라면 처음부터 `dynamic=True`를 주거나 batch 크기를 몇 개로 고정합니다.
- **mode로 최적화 강도를 고릅니다.** `"default"`, CUDA Graph로 launch 오버헤드를 더 줄이는 `"reduce-overhead"`, kernel 후보를 실제로 돌려 보고 고르는 `"max-autotune"`(컴파일이 훨씬 오래 걸림)이 있습니다. 이 글의 실습은 기본 모드입니다.
- **정밀도는 바꾸지 않습니다.** `torch.compile`은 실행 방식을 바꿀 뿐이라 FP32 모델은 FP32로 돌아갑니다. FP16과 함께 쓰려면 `.half()`한 모델을 compile하거나 autocast 안에서 호출합니다.

### 2.4 PyTorch 내장 최적화 vs TensorRT

| 구분 | `.half()` | `torch.autocast` | `torch.compile` | TensorRT |
| --- | --- | --- | --- | --- |
| **하는 일** | 모델 전체를 FP16으로 | 연산별로 FP32/FP16 혼합 | 그래프 캡처 + 연산 융합(Triton kernel 생성) | 레이어 융합, GPU별 kernel(tactic) 선택 |
| **바꾸는 것** | 정밀도 | 정밀도 | 실행 방식 | 실행 방식 (정밀도는 ONNX를 따름, 3.6절) |
| **적용 난이도** | 한 줄 | `with` 한 줄 | 한 줄 (첫 호출 컴파일) | 높음 (ONNX 변환, engine 빌드, GPU·버전별 관리) |
| **실행 환경** | PyTorch, 추론 위주 | PyTorch, 학습·추론 | PyTorch, 학습·추론 | PyTorch 불필요(C++ 런타임 단독 가능), 추론 전용 |

정밀도를 바꾸는 방법(`.half()`, autocast)과 실행 방식을 바꾸는 방법(`torch.compile`, TensorRT)은 겹치지 않으므로 함께 쓸 수 있습니다. TensorRT는 `torch.compile`보다 더 깊이 최적화하는 대신 PyTorch 밖으로 나가야 합니다.
TensorRT 10까지는 빌드 플래그로 FP16을 켜면 빌더가 레이어별 정밀도까지 골랐지만, 이 글에서 쓰는 TensorRT 11은 ONNX에 적힌 정밀도를 그대로 따릅니다(3.6절). 그래서 FP16 engine도 `.half()`로 정밀도를 먼저 정한 뒤 만듭니다.

두 진영을 잇는 **Torch-TensorRT**도 있습니다. `import torch_tensorrt` 후 `torch.compile(model, backend="tensorrt")`로 호출하면, TensorRT로 변환할 수 있는 subgraph만 engine으로 바꾸고 나머지는 PyTorch로 실행합니다.

정리하면 다음과 같습니다.

- **학습 속도를 높이고 싶다**: `torch.autocast` + `torch.compile`. TensorRT는 추론 전용입니다.
- **추론을 간편하게 빠르게 하고 싶다**: PyTorch 환경을 유지한 채 FP16 + `torch.compile`부터 적용합니다.
- **latency를 끝까지 줄이거나 GPU 비용을 아껴야 한다**: 번거롭더라도 TensorRT engine으로 변환하고, 필요하면 Triton Inference Server로 서빙합니다.

얼마나 빨라지는지는 모델·batch·GPU마다 크게 다르므로 일반적인 배수보다는 직접 측정하는 편이 정확합니다. 5장에서 T4 + ResNet-18 기준으로 비교합니다.

## 3. TensorRT

### 3.1 TensorRT는 딥러닝 모델의 컴파일러다

`torch.compile`도 컴파일러지만, PyTorch 런타임 안에서 실행되고 프로세스가 뜰 때마다 첫 호출에서 다시 컴파일합니다. TensorRT는 한 걸음 더 나가 C/C++ 컴파일처럼 **미리 빌드한 결과물을 파일로 남깁니다.**

| C/C++ | TensorRT |
| --- | --- |
| 소스 코드(`.c`, `.cpp`) | 모델 정의(ONNX) |
| 컴파일러(gcc, clang) | TensorRT Builder |
| 타깃 CPU 지정(x86, ARM, `-march=native`) | 빌드하는 GPU 아키텍처(sm75, sm89, …) |
| 컴파일 최적화(인라이닝, 루프 전개 등) | 레이어 융합, 레이어별 kernel(tactic) 선택 |
| 실행 파일(binary) | engine 파일(`.engine`) |

ARM용으로 컴파일한 바이너리가 x86에서 실행되지 않듯, T4 GPU에서 빌드한 engine은 L4 GPU에서 실행되지 않습니다.
대신 컴파일된 바이너리가 인터프리터로 실행하는 코드보다 빠르듯, engine은 PyTorch가 레이어를 하나씩 실행하는 방식보다 빠릅니다.
빌드할 때 지정한 GPU와 입력 shape에 맞춰 연산을 미리 합치고, 레이어마다 가장 빠른 구현을 골라 고정해 두기 때문입니다.
gcc와 다른 점은, TensorRT는 어떤 구현이 빠른지를 규칙으로 추정하지 않고 **빌드하는 GPU에서 직접 실행해 측정**한다는 것입니다.

### 3.2 왜 빌드가 필요한가

정렬도 데이터 상태(거의 정렬됨, 값의 범위가 좁음 등)에 따라 가장 빠른 알고리즘이 달라집니다.
GPU의 딥러닝 연산(예: Convolution)에서는 이 차이가 훨씬 큽니다.
**모든 상황에서 가장 빠른 kernel 하나는 없습니다.**
성능은 다음 요인에 따라 달라집니다.

1. **입력 shape**: batch 크기, 채널 수($C$), 높이·너비($H, W$)에 따라 메모리 접근 패턴이 달라집니다.
2. **연산 파라미터**: 필터가 $3 \times 3$인지 $7 \times 7$인지, stride와 padding이 얼마인지에 따라 효율적인 계산 방식이 달라집니다.
3. **GPU 아키텍처**: Turing, Ampere, Hopper 등 세대마다 Tensor Core 구조, 캐시 크기, shared memory 용량이 다릅니다. 어떤 kernel은 한 세대에서 가장 빠르지만 다음 세대에서는 다른 kernel이 더 빠를 수 있습니다.

그래서 NVIDIA는 연산마다 구현 후보(tactic)를 여러 개 준비해 둡니다. 예를 들면 이런 식입니다.

- **후보 a**: 메모리를 적게 쓰지만 연산 오버헤드가 있음 (작은 입력에 유리)
- **후보 b**: 메모리를 많이 쓰지만 병렬성을 끌어올려 빠름 (큰 입력에 유리)
- **후보 c**: 채널 수가 특정 배수(예: FP16 Tensor Core라면 8의 배수)일 때만 매우 빠름

TensorRT는 engine을 빌드할 때 **실제로 추론할 GPU에서** 각 레이어의 shape으로 후보들을 직접 실행해 보고(profiling), "이 레이어는 이 GPU에서 c가 0.12ms로 가장 빠르다"는 식으로 하나를 고릅니다.
이 과정에서 Conv + BatchNorm + ReLU처럼 이어진 레이어를 하나의 kernel로 합치는 레이어 융합(Layer fusion)도 함께 일어납니다.

빌드가 끝나면 고른 tactic 조합이 engine 파일(`.engine` 또는 `.plan`)에 고정됩니다.
추론할 때는 해당 파일을 불러와 바로 그 kernel을 실행합니다.
대신 그 선택은 빌드한 GPU를 전제로 한 것이므로, **engine은 같은 GPU 아키텍처와 같은 TensorRT 버전에서만 재사용할 수 있습니다.**
T4(sm75) GPU에서 빌드한 engine은 L4(sm89) GPU가 장착된 서버에서 사용할 수 없습니다.
아키텍처가 같아도 GPU 모델이 다르면(SM 수, 메모리 대역폭이 다르면) 측정 결과가 맞지 않아 최적이 아닐 수 있으므로, 배포할 GPU와 같은 모델에서 빌드하는 것이 안전합니다.
(Ampere 이후 GPU끼리 호환되게 빌드하는 hardware compatibility 옵션도 있지만, 그만큼 속도를 일부 포기합니다.)

### 3.3 TensorRT 아키텍처

TensorRT의 Python API는 객체 이름이 많아 처음 보면 헷갈립니다. 하지만 **빌드 단계**와 **추론 단계**로 나누면 단순합니다.
빌드 단계는 "무엇을(network) 어떻게(config) 컴파일할지" 정해 engine 파일을 만들고, 추론 단계는 그 파일을 읽어 실행합니다.
두 단계는 다른 프로세스, 다른 시점에 실행해도 됩니다. 보통 빌드는 배포 전에 한 번, 추론은 서버가 뜰 때마다 합니다.

| 객체 | 단계 | 역할 |
| --- | --- | --- |
| `Logger` | 공통 | TensorRT 내부 메시지(경고·에러) 출력 |
| `Builder` | 빌드 | 네트워크를 GPU에 맞게 최적화해 engine 생성 |
| `INetworkDefinition` | 빌드 | 모델 구조를 담는 그릇 (**무엇을**) |
| `OnnxParser` | 빌드 | ONNX 파일을 읽어 network를 채움 |
| `IBuilderConfig` | 빌드 | 메모리 한도, 최적화 프로파일, timing cache 등 옵션 (**어떻게**) |
| `Runtime` | 추론 | engine 파일을 역직렬화 |
| `ICudaEngine` | 추론 | 최적화된 모델 (가중치 + 실행 계획). 읽기 전용 |
| `IExecutionContext` | 추론 | 한 번의 실행을 위한 상태와 작업 공간 |

전체 관계를 그리면 다음과 같습니다.

```text
[ 1. Build Phase (컴파일 타임) ]

  Logger, IErrorRecorder, IGpuAllocator   (기반 인프라 주입)
         │
         ▼
  Builder ──create_network()──> INetworkDefinition <──parse()── OnnxParser (model.onnx)
     │
     └──create_builder_config()──> IBuilderConfig   (Workspace·프로파일 등 빌드 옵션)
                                       ├── IOptimizationProfile (Dynamic Shape 범위)
                                       └── ITimingCache         (tactic 측정 결과 재사용 → 빌드 가속)

  Builder.build_serialized_network(network, config)
         │
         ▼
  [ Serialized Engine (.engine 파일) ]

────────────────────────────────────────────────────────────────────────────

[ 2. Runtime Phase (추론 타임) ]

  Runtime ──deserialize_cuda_engine()──> ICudaEngine (불변의 엔진 모델)
                                               │
                     ┌─────────────────────────┼─────────────────────────┐
                     ▼                         ▼                         ▼
           IEngineInspector           IExecutionContext            Refitter
           (레이어 구조 분석)          (추론 실행 컨텍스트)          (가중치 교체, refit 빌드 시)
                                               │
                                               ▼
                                         IProfiler
                                     (레이어별 실행 시간 측정)
```

몇 가지 짚어 둘 점입니다.

- **network는 "무엇을", config는 "어떻게"입니다.** 같은 network라도 config(workspace 한도, 최적화 프로파일 등)가 다르면 다른 engine이 나옵니다.
- **`ICudaEngine`은 무겁고 불변, `IExecutionContext`는 가볍고 상태를 가집니다.** engine은 가중치와 실행 계획을 담고 있어 GPU 메모리를 많이 쓰고, 한 번 만들면 바뀌지 않습니다. 반면 context는 입출력 주소, 입력 shape, 중간 activation 메모리 같은 실행 상태를 가집니다. 그래서 여러 요청을 동시에 처리하려면 engine 하나에서 context를 여러 개 만들어 각각 다른 CUDA stream에서 실행합니다.
- **Refitter는 engine에 붙습니다.** refit 플래그를 켜고 빌드한 engine이라면, 다시 빌드하지 않고 가중치만 바꿔 끼울 수 있습니다. 구조는 그대로라 fine-tuning한 가중치를 반영할 때 씁니다.

### 3.4 기본 흐름 ①: engine build (torch → ONNX → TensorRT engine)

가장 단순한 형태로 전체 흐름을 보면 세 단계입니다.

```text
PyTorch 모델 ──torch.onnx.export──> model.onnx ──TensorRT Builder──> model.engine
```

**① PyTorch → ONNX**

```python
import torch, torchvision

model = torchvision.models.resnet18(weights="DEFAULT").eval().cuda()
dummy = torch.randn(1, 3, 224, 224, device="cuda")   # 이 shape으로 입력이 고정된다

torch.onnx.export(
    model, (dummy,), "model.onnx",
    input_names=["input"], output_names=["output"],   # engine에서 이 이름으로 입출력을 찾는다
    opset_version=17,
)
```

**② ONNX → TensorRT engine**

```python
import tensorrt as trt

logger = trt.Logger(trt.Logger.WARNING)
builder = trt.Builder(logger)
network = builder.create_network()    # TRT 10부터 explicit batch가 기본이라 플래그 없음

parser = trt.OnnxParser(network, logger)
with open("model.onnx", "rb") as f:
    if not parser.parse(f.read()):
        for i in range(parser.num_errors):
            print(parser.get_error(i))
        raise RuntimeError("ONNX 파싱 실패")

config = builder.create_builder_config()
config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, 1 << 30)   # 1GB

# FP16 engine을 만들려면
#   - TRT 10 이하: config.set_flag(trt.BuilderFlag.FP16)
#   - TRT 11     : 플래그가 없다. FP16으로 export한 ONNX를 넣는다 (3.6절)

engine_bytes = builder.build_serialized_network(network, config)   # tactic 측정: 수십 초~수 분

with open("model.engine", "wb") as f:
    f.write(engine_bytes)
```

3.3의 표와 그대로 대응합니다.
`Builder`가 빈 `network`를 만들고, `OnnxParser`가 그 안을 ONNX 그래프로 채우고, `config`에 옵션을 담아 `build_serialized_network`로 컴파일합니다.
결과는 바로 실행할 수 있는 객체가 아니라 **직렬화된 bytes**이고, 이를 파일로 저장해 두면 다음부터는 빌드 없이 불러올 수 있습니다.

### 3.5 기본 흐름 ②: engine load → 추론

```python
import tensorrt as trt
import torch

logger = trt.Logger(trt.Logger.WARNING)
runtime = trt.Runtime(logger)

with open("model.engine", "rb") as f:
    engine = runtime.deserialize_cuda_engine(f.read())
context = engine.create_execution_context()

# 입출력 GPU 메모리는 torch 텐서를 그대로 쓴다
inp = torch.randn(1, 3, 224, 224, device="cuda", dtype=torch.float32)
out = torch.empty(1, 1000, device="cuda", dtype=torch.float32)

# export 때 정한 이름 ↔ GPU 주소 연결
context.set_tensor_address("input", inp.data_ptr())
context.set_tensor_address("output", out.data_ptr())

stream = torch.cuda.current_stream()
context.execute_async_v3(stream_handle=stream.cuda_stream)
stream.synchronize()

print(out.argmax(dim=1))
```

흐름은 `Runtime`으로 engine 파일을 역직렬화 → engine에서 context 생성 → 입출력 텐서 주소 연결 → 실행 순서입니다.

- **입출력은 이름으로 찾습니다.** `"input"`, `"output"`은 ①에서 `input_names`/`output_names`로 준 이름입니다. 이름을 안 주면 export가 자동으로 붙인 이름을 써야 하므로 꼭 지정해 둡니다.
- **입출력 메모리는 직접 준비합니다.** 중간 activation 메모리는 context가 잡지만, 입출력 버퍼는 할당해 주지 않고 주소만 받습니다. torch 텐서의 `data_ptr()`이 GPU 주소이므로 pycuda 같은 별도 라이브러리 없이 torch로 할당하면 됩니다. 출력 텐서의 shape과 dtype은 engine과 정확히 맞아야 합니다.
- **실행은 비동기입니다.** `execute_async_v3`는 kernel을 stream에 올리고 바로 돌아옵니다. 결과를 CPU에서 보려면 `synchronize()`로 끝나기를 기다립니다. torch의 현재 stream에 올렸으므로, 결과를 바로 다음 torch 연산에 넘길 때는 torch가 순서를 보장해 줍니다.

### 3.6 정밀도: TensorRT 11은 ONNX가 정한다

TensorRT 10까지는 FP32 ONNX를 넣고 `config.set_flag(trt.BuilderFlag.FP16)`를 켜면, 빌더가 레이어마다 FP32와 FP16 중 빠른 쪽을 골라 썼습니다(weakly typed).
편리하지만 어느 레이어가 FP16으로 돌지 빌더가 정하므로, 같은 ONNX라도 GPU나 버전에 따라 정밀도가 달라질 수 있었습니다.

TensorRT 11은 *strongly typed* 네트워크만 지원합니다. 각 레이어의 정밀도는 ONNX에 적힌 dtype을 그대로 따르고, `BuilderFlag.FP16` 같은 정밀도 플래그는 없습니다.
그래서 FP16 engine을 원하면 **FP16 모델을 ONNX로 export**합니다. 2.1의 `.half()`가 여기서 다시 쓰입니다.

```python
model_fp16 = copy.deepcopy(model).half()
torch.onnx.export(model_fp16, (dummy.half(),), "model_fp16.onnx", ...)
```

정밀도 결정이 PyTorch 쪽으로 옮겨 온 셈이라, `.half()` 모델로 정확도를 먼저 확인하고 그대로 export하면 engine의 정밀도도 같다는 장점이 있습니다.

## 4. 실습: ResNet-18로 네 가지 방법 적용하기

* **실습 환경**
    * **플랫폼:** Colab
    * **하드웨어:** Tesla T4 (Turing, sm75)
    * **소프트웨어:** PyTorch 2.14, TensorRT 11.4

* **모델:** pretrained ResNet-18 (Image 분류 모델)

* **입력 데이터**
    * **데이터셋:** Oxford-IIIT Pet 실제 사진 8장
    * **전처리:** ImageNet 표준 전처리
    * **텐서 형태:** `[8, 3, 224, 224]` 배치

### 4.1 PyTorch 방식

```python
B = 8
model = torchvision.models.resnet18(weights="DEFAULT").eval().cuda()
x = data.imagenet_batch(B)  # [8, 3, 224, 224]

# FP16
model_fp16 = copy.deepcopy(model).half()
x_fp16 = x.half()

# autocast: 모델·입력은 FP32 그대로
model_autocast = copy.deepcopy(model)
def run_autocast(inp):
    with torch.amp.autocast("cuda", dtype=torch.float16):
        return model_autocast(inp)

# torch.compile (기본 모드)
model_compiled = torch.compile(copy.deepcopy(model))
model_compiled_fp16 = torch.compile(copy.deepcopy(model_fp16))
```

### 4.2 PyTorch → ONNX

```python
torch.onnx.export(
    model, (x,), "resnet18_b8.onnx",
    input_names=["input"], output_names=["logits"],
    opset_version=17, dynamo=False,
)

# FP16 engine용: FP16 모델 자체를 export한다 (3.6절)
torch.onnx.export(
    model_fp16, (x_fp16,), "resnet18_fp16_b8.onnx",
    input_names=["input"], output_names=["logits"],
    opset_version=17, dynamo=False,
)
```

- **입력 shape은 export할 때의 `x`로 고정됩니다.** 이 ONNX로 만든 engine은 `[8, 3, 224, 224]` 전용이며, batch나 해상도가 다른 입력을 넣으면 실행이 실패합니다. 여러 shape을 받으려면 dynamic shape을 설정해야 합니다.
- FP16 ONNX는 파일 크기도 46.7MB → 23.4MB로 절반이 됩니다.

### 4.3 engine 빌드

3.4의 코드를 함수로 감싼 것입니다. FP32·FP16 ONNX를 각각 넣어 engine 두 개를 만듭니다.

```python
import tensorrt as trt

def build_engine(onnx_path, engine_path):
    logger = trt.Logger(trt.Logger.WARNING)  # 빌드 과정을 자세히 보려면 VERBOSE
    builder = trt.Builder(logger)

    # TRT 11은 strongly typed가 기본이라 별도 플래그가 필요 없다
    network = builder.create_network()
    parser = trt.OnnxParser(network, logger)
    with open(onnx_path, "rb") as f:
        if not parser.parse(f.read()):
            for i in range(parser.num_errors):
                print(parser.get_error(i))
            raise RuntimeError("ONNX 파싱 실패")

    config = builder.create_builder_config()
    config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, 1 << 30)  # kernel 임시 메모리 1GB

    # 현재 GPU에서 레이어별로 가장 빠른 kernel을 고른다
    engine_bytes = builder.build_serialized_network(network, config)
    if engine_bytes is None:
        raise RuntimeError("engine 빌드 실패")

    with open(engine_path, "wb") as f:
        f.write(engine_bytes)
```

engine은 GPU 아키텍처와 TensorRT 버전에 묶이므로, 실습 코드에서는 파일명에 둘 다 넣습니다(e.g., `resnet18_b8_tesla-t4-sm75_trt11.4.0.106.engine`).
다른 GPU에서 빌드한 engine을 실수로 불러오는 일을 파일명 단계에서 막기 위해서입니다.

> - resnet18: 모델 이름
> - b8: 배치 사이즈 (Batch Size = 8)
> - tesla-t4-sm75: GPU 모델과 아키텍처 (Tesla T4, Compute Capability 7.5)
> - trt11.4.0.106: TensorRT 버전

### 4.4 engine 로드와 추론

3.5의 코드에서 출력 버퍼를 engine이 알려주는 shape으로 만들도록 바꾸고, `model(x)`처럼 호출할 수 있게 함수로 감쌌습니다.

```python
runtime = trt.Runtime(trt.Logger(trt.Logger.WARNING))
with open(engine_path, "rb") as f:
    engine = runtime.deserialize_cuda_engine(f.read())
assert engine is not None, "다른 GPU 아키텍처/TRT 버전에서 빌드된 engine일 수 있음"
context = engine.create_execution_context()

def trt_infer(context, x):
    x = x.contiguous()  # TensorRT는 연속된 메모리를 가정한다
    out = torch.empty(tuple(context.get_tensor_shape("logits")), dtype=x.dtype, device="cuda")

    context.set_tensor_address("input", x.data_ptr())
    context.set_tensor_address("logits", out.data_ptr())

    # torch와 같은 CUDA stream에서 실행 → 이후 torch 연산이 자동으로 완료를 기다린다
    ok = context.execute_async_v3(torch.cuda.current_stream().cuda_stream)
    assert ok, "TensorRT 실행 실패"
    return out
```

한 가지 주의할 점은 `engine` 객체의 수명입니다. 
`context`가 쓰이는 동안 `engine`이 garbage collection되면 안 되므로 변수를 지우지 않고 유지합니다.

## 5. 정확도 & 속도 비교

* **실험 조건 및 입력**
    * **입력 데이터:** 실제 이미지 8프레임 배치(batch size = 8)

* **측정 방법 및 조건**
    * **Warmup:** 20회 (측정에서 제외. `torch.compile`의 컴파일도 이 단계에서 끝남)
    * **반복 횟수:** 100회 반복 측정
    * **측정 도구:** CUDA Event를 활용한 GPU 실행 시간 측정

* **모델 최적화 설정**
    * **`torch.compile`:** 기본(Default) 모드 적용

### 속도

| 방식 | mean (ms) | p50 (ms) | p90 (ms) | speedup |
| --- | ---: | ---: | ---: | ---: |
| PyTorch FP32 | 9.877 | 9.884 | 9.989 | 1.00x |
| PyTorch FP16 (`.half()`) | 4.365 | 4.331 | 4.413 | 2.26x |
| PyTorch autocast | 4.906 | 4.431 | 6.155 | 2.01x |
| PyTorch compile FP32 | 9.686 | 9.654 | 9.837 | 1.02x |
| PyTorch compile FP16 | 2.826 | 2.644 | 3.933 | 3.49x |
| TensorRT FP32 | 7.735 | 7.720 | 7.834 | 1.28x |
| **TensorRT FP16** | **1.934** | **1.922** | **2.006** | **5.11x** |

speedup은 PyTorch FP32의 mean 대비 배수입니다.

### 정확도

PyTorch FP32의 출력(logit)을 기준으로, 각 방식의 출력이 얼마나 달라졌는지 비교했습니다.

| 방식 | max_diff | rel_err | cos_sim | top-1 일치 |
| --- | ---: | ---: | ---: | ---: |
| PyTorch FP32 | 0.0000 | 0 | 1.000000 | 100.0% |
| PyTorch FP16 (`.half()`) | 0.0244 | 1.81e-3 | 0.999997 | 100.0% |
| PyTorch autocast | 0.0176 | 9.97e-4 | 0.999999 | 100.0% |
| PyTorch compile FP32 | 0.0000 | 1.03e-6 | 1.000000 | 100.0% |
| PyTorch compile FP16 | 0.0254 | 1.78e-3 | 0.999998 | 100.0% |
| TensorRT FP32 | 0.0000 | 1.15e-6 | 1.000000 | 100.0% |
| TensorRT FP16 | 0.0536 | 3.50e-3 | 0.999993 | 100.0% |

- **max_diff**: logit의 최대 절대 오차
- **rel_err**: 상대 오차 $\lVert y - y_{\text{base}} \rVert / \lVert y_{\text{base}} \rVert$. logit 크기와 무관하게 비교할 수 있습니다.
- **cos_sim**: 샘플별 logit 벡터 코사인 유사도의 최솟값
- **top-1 일치**: 기준과 top-1 예측 클래스가 같은 비율

### 해석

결과를 다섯 가지로 정리했습니다.

#### 1. FP32에서는 어떤 최적화도 효과가 작다 (1.02배 ~ 1.28배)

* **수치**
    - `torch.compile` (FP32): 1.02배
    - TensorRT (FP32): 1.28배
* **원인**
    - T4는 Turing 세대라 **FP32 연산에는 Tensor Core를 쓸 수 없습니다** (TF32는 Ampere부터 지원).
    - ResNet-18의 시간 대부분은 Conv가 차지하는데, `torch.compile`은 Conv를 cuDNN 그대로 호출하고 그 사이의 elementwise 연산만 합칩니다. 그래서 eager와 거의 차이가 없습니다.
    - TensorRT는 Conv + BN + ReLU를 하나로 합치고 Conv kernel도 직접 골라서 조금 더 빨라지지만, CUDA 코어의 FP32 연산 성능이라는 상한은 넘지 못합니다.

#### 2. FP16으로 바꾸기만 해도 2배 이상 빨라진다

* **수치**
    - `.half()`: 2.26배
    - `autocast`: 2.01배
* **원인**
    - **FP16부터 Tensor Core를 쓸 수 있게 되는 것**이 결정적입니다. 메모리 읽기·쓰기 양이 절반이 되는 것도 보탭니다.
* **`.half()`와 `autocast`의 차이**
    - p50 기준으로는 거의 같습니다(4.331ms vs 4.431ms). ResNet-18은 Conv·Linear가 연산의 대부분이고, `autocast`도 이들을 FP16으로 실행하기 때문입니다.
    - `autocast`의 mean이 더 높은 것은 p90이 6.155ms로 튀는 반복이 간헐적으로 섞였기 때문입니다.

#### 3. `torch.compile`은 FP16과 함께 쓸 때 효과가 난다

* **수치**
    - FP32에서는 1.02배에 그쳤지만, FP16 모델에 적용하면 4.365ms → 2.826ms로 **1.54배 더 빨라졌습니다.**
* **원인**
    - FP16으로 Conv가 빨라지면, 그 사이에 끼어 있는 elementwise 연산과 kernel launch가 전체 시간에서 차지하는 비중이 커집니다.
    - `torch.compile`이 줄이는 것이 바로 이 부분입니다. 정밀도와 실행 방식을 함께 바꿔야 하는 이유입니다.

#### 4. TensorRT + FP16이 가장 빠르고 latency도 고르다

* **수치**
    - PyTorch FP16 대비 **2.26배** (4.365ms → 1.934ms)
    - `torch.compile` FP16 대비 **1.46배** (2.826ms → 1.934ms)
* **원인**
    * 레이어 융합으로 kernel 수와 메모리 왕복 감소
    * T4에서 직접 측정해 고른 tactic
    * Python에서 연산마다 kernel을 띄우는 오버헤드 제거
* **안정성**
    - p90이 2.006ms로 mean과 거의 차이가 없습니다. 같은 FP16 계열에서 `autocast`(p90 6.155ms)·`torch.compile` FP16(p90 3.933ms)은 가끔 튀는 반복이 있었던 것과 대조적입니다.

#### 5. 정확도 손실은 작지만, 실제 데이터로 다시 확인해야 한다

* **정확도 영향**
    * **FP32 방식**: 상대 오차 `1e-6` 수준 (사실상 같은 출력)
    * **FP16 방식**: 상대 오차 `1e-3` 수준 (TensorRT FP16이 `3.5e-3`으로 가장 큼)
    * 코사인 유사도는 모두 **0.99999 이상**, top-1 예측은 **모두 일치**했습니다.
    * `autocast`의 오차(`9.97e-4`)가 `.half()`(`1.81e-3`)보다 작은 것은, Conv·Linear 외의 연산(BatchNorm의 scale·shift 등)이 FP32 파라미터로 계산되기 때문으로 보입니다.
* **주의할 점**
    - 사진 8장으로 본 결과이므로, 실제 배포 전에는 **검증셋 전체로 정확도를 확인해야 합니다.**
    - 특히 얼굴 임베딩처럼 출력 벡터의 유사도로 판정하는 모델은 threshold 근처의 판정이 뒤집히지 않는지 확인해야 합니다.

이 수치는 T4 + ResNet-18 + batch 8이라는 한 조건의 결과입니다.
Ampere 이후 GPU에서는 FP32 연산에도 TF32 Tensor Core를 쓸 수 있고, 모델이나 batch가 크면 launch 오버헤드의 비중이 줄어 배수가 달라집니다.
어디서나 통하는 정답은 없으니, 배포할 GPU와 모델로 다시 측정해야 합니다.

## 마치며

이 글에서 다룬 방법은 **연산 정밀도**와 **실행 방식**이라는 두 축으로 나뉩니다.

- **연산 정밀도**
    - **`.half()`, `autocast`**: 데이터 타입을 FP32 → FP16으로 낮춰 Tensor Core를 쓰고 메모리 대역폭을 아낍니다.
- **실행 방식**
    - **`torch.compile`**: 실행 시점에 연산 그래프를 캡처해 kernel을 합치고, Python 실행 오버헤드를 줄입니다.
    - **`TensorRT`**: PyTorch 밖에서 그래프를 재구성(레이어 융합)하고, 특정 GPU에서 가장 빠른 kernel(tactic)을 미리 측정해 고정하는 전용 실행 엔진입니다.

두 축은 서로 독립이라 함께 쓸 수 있습니다.
이번 실습에서도 가장 큰 향상은 FP16 전환에서 나왔고, 그 위에 `torch.compile`이나 TensorRT를 얹었을 때 추가로 빨라졌습니다.

> ⚠️ **결과가 원본과 bit 단위로 같지는 않습니다**
>
> 1. **정밀도 축(FP16, autocast)**: 유효 자릿수와 표현 범위가 줄어 오차가 누적되거나 아주 작은 값이 0이 될 수 있습니다. 대부분의 모델은 정확도가 거의 그대로지만, 정밀도가 중요한 도메인이라면 별도 검증이 필요합니다.
> 2. **실행 방식 축(`torch.compile`, TensorRT)**: FP32를 유지해도 연산 순서 변경, kernel 융합, 다른 kernel 선택 때문에 소수점 아래 미세한 차이가 생깁니다(이번 실험의 상대 오차 `1e-6` 수준).

### TensorRT engine의 제약

TensorRT engine 빌드는 "이 GPU에서, 이 입력 shape일 때 가장 빠른 kernel이 무엇인가"를 미리 측정해 고정하는 과정입니다.
그래서 빠른 대신 engine이 GPU 아키텍처, TensorRT 버전, 입력 shape에 묶입니다.
이번에 만든 engine도 T4에서, 정확히 `[8, 3, 224, 224]` 입력만 처리할 수 있습니다.

### 다음 과제: Dynamic Shape

실제 CCTV 파이프라인에서는 프레임마다 검출되는 얼굴 수가 달라서, 임베딩 모델에 들어가는 batch 크기가 계속 바뀝니다.

batch 크기별로 engine을 따로 만들어 골라 쓸 수도 있지만, engine마다 가중치를 따로 들고 있어 GPU 메모리가 늘고 빌드·관리할 파일도 많아집니다.

다음 글에서는 Dynamic Shape을 적용해, engine 하나로 여러 batch 크기를 처리하는 방법을 다룹니다.
