> **TL;DR**
>
> **1. static engine에 다른 batch를 넣어도 예외가 나지 않습니다.**
> - `set_input_shape`는 실패하면 `False`만 반환하고, engine은 원래 batch 분량의 메모리를 그대로 읽습니다.
> - 결과는 **조용히 틀린 출력**이거나, 운이 나쁘면 **illegal memory access로 프로세스 전체가 망가지는 것**입니다.
>
> **2. 먼저 shape을 검증해 명시적인 에러로 바꿉니다.**
> - `set_input_shape`의 반환값이 `False`면 메모리를 건드리기 전에 예외를 던집니다. static이든 dynamic이든 필요합니다.
>
> **3. 여러 batch를 받으려면 두 군데를 바꿉니다.**
> - **ONNX export**: `dynamic_shapes`로 batch 축을 동적으로 표시
> - **TensorRT build**: optimization profile로 범위(`min`/`max`)와 기준 shape(`opt`) 지정
>
> **4. T4 + ResNet-18, profile `1 / 8 / 32`**
> - engine 하나로 batch 1·3·8·32를 모두 처리하고, PyTorch 대비 max diff 약 `1e-5`, top-1 100% 일치
> - batch 33은 profile 범위 밖이라 검증 단계에서 거부

## Intro

[이전 글](#/post/2026-11-15-cctv-opt-1.md)에서는 ResNet-18을 TensorRT engine으로 바꿔 PyTorch FP32 대비 최대 5배 빠르게 만들었습니다.
다만 그 engine은 `[8, 3, 224, 224]`, 즉 **batch 8 입력 하나만** 받을 수 있었습니다.

GPU는 데이터를 한 장씩보다 묶음(batch)으로 처리할 때 훨씬 효율적이라, 추론 코드는 보통 데이터를 batch 단위로 잘라 모델에 넣습니다.
그런데 실제로 데이터를 돌려 보면 batch 크기와 맞지 않는 입력이 꼭 생깁니다.

- **마지막 묶음이 모자라는 경우**: batch 크기가 8인데 이미지가 35장이면, 8장씩 4번 돌고 **3장이 남습니다.**
- **단일 데이터를 처리해야 하는 경우**: batch 처리용으로 engine을 만들었는데, 실시간 요청처럼 **이미지 한 장**을 바로 처리해야 할 때가 있습니다.
- **입력 개수가 매번 다른 경우**: 한 프레임에서 검출된 객체마다 후속 모델을 돌리면, 프레임마다 batch 크기가 달라집니다.

### 흔히 쓰는 대처 방법

**① batch 크기마다 engine을 따로 둔다**

batch 1, 2, 4, 8용 engine을 각각 빌드해 두고, 입력 크기에 맞는 engine을 고릅니다.
각 engine이 자기 shape에 최적화되어 있어 속도는 가장 좋지만, engine마다 가중치를 따로 들고 있어 GPU 메모리가 engine 수만큼 늘어납니다.
빌드 시간과 관리할 파일도 GPU 아키텍처 × TensorRT 버전 × batch 크기만큼 늘어납니다.

**② 빈 자리를 dummy 데이터로 채운다(padding)**

3장이 남았다면 0으로 채운 이미지 5장을 붙여 8장으로 만들고, 출력에서 앞 3개만 씁니다.

```python
def pad_to(x, batch_size):
    n = x.shape[0]
    pad = torch.zeros(batch_size - n, *x.shape[1:], dtype=x.dtype, device=x.device)
    return torch.cat([x, pad]), n

x_padded, n = pad_to(x_rest, 8)       # [3, ...] → [8, ...]
y = trt_infer(context, x_padded)[:n]  # 앞 n개만 사용
```

engine 하나로 해결되고 구현도 간단합니다.
대신 버려질 dummy 데이터에도 연산을 똑같이 하므로, 이미지 1장을 처리할 때도 8장 분량의 시간이 걸립니다.

**③ engine 하나가 여러 batch를 받게 한다(dynamic shape)**

이 글에서 다루는 방법입니다. 다만 그 전에 짚고 넘어가야 할 것이 있습니다.
**static engine에 다른 batch를 그냥 넣으면 어떻게 될까요?** 에러가 날 것 같지만, 그렇지 않습니다.

## 1. static engine에 다른 shape의 tensor를 넣으면

### 1.1 실험: batch 8 engine에 batch 4 넣기

이전 글과 같은 방법으로 8장의 Image 데이터를 batch로 받는 `[8, 3, 224, 224]` 전용 static engine을 만든 후 
4장의 Image 데이터인 `[4, 3, 224, 224]` batch data를 engine에 입력하면 어떻게 될까요?

```python
def trt_infer_unchecked(context, x):
    """set_input_shape의 반환값을 확인하지 않는 추론 함수 (잘못된 예)"""
    x = x.contiguous()
    context.set_input_shape("input", tuple(x.shape))   # 반환값을 버린다

    out = torch.empty(tuple(context.get_tensor_shape("logits")), dtype=x.dtype, device="cuda")
    context.set_tensor_address("input", x.data_ptr())   # TensorRT는 주소만 받는다
    context.set_tensor_address("logits", out.data_ptr())
    ok = context.execute_async_v3(torch.cuda.current_stream().cuda_stream)
    assert ok, "TensorRT 실행 실패"
    return out
```

입력은 일부러 **8장 image tensor의 앞 4장을 잘라낸 view**로 만듭니다.
view는 원본과 메모리를 공유하므로, batch 4 tensor 바로 뒤에는 원본의 나머지 4장이 있습니다.
이렇게 하면 TensorRT가 범위 밖을 읽더라도 그 자리는 실제로 할당된 메모리라 crash가 나지 않고, 밖에서 **무엇을** 읽었는지 알고 있으니 결과로 확인할 수 있습니다.

```python
batches = {8: data.imagenet_batch(8)}   # 실제 사진 8장 [8, 3, 224, 224]
batches[4] = batches[8][:4]             # view: 같은 메모리의 앞 절반
assert batches[4].data_ptr() == batches[8].data_ptr()

outputs = {b: trt_infer_unchecked(context, batches[b]) for b in (8, 4)}

print(outputs[4].shape)                                  # 4장을 넣었는데?
print((outputs[4][:4] - outputs[8][:4]).abs().max())     # batch 4 안의 이미지
print((outputs[4][4:] - outputs[8][4:]).abs().max())     # batch 4 밖의 이미지
```
결과:
```text
[TRT ERROR] IExecutionContext::setInputShape: Error Code 3: API Usage Error (Parameter check failed,
  condition: engineDims.d[i] == dims.d[i]. Static dimension mismatch while setting input shape for input.
  Set dimensions are [4,3,224,224]. Expected dimensions are [8,3,224,224]. ...)

torch.Size([8, 1000])     ← 4장을 넣었는데 출력은 8개
tensor(0.)                ← 앞 4개: batch 4 안의 이미지 결과
tensor(0.)                ← 뒤 4개: batch 4 밖(원본의 5~8번째)의 이미지 결과
```

일어난 일을 순서대로 보면 다음과 같습니다.

![batch 8 static engine에 batch 4 입력을 넣었을 때: TensorRT는 입력 주소에서 8장 분량을 읽어 버퍼 밖 4장까지 참조하고, 출력 8개 중 뒤 4개는 출처를 알 수 없는 데이터로 연산한 값이 된다](/images/cctv-opt-2/tensorrt-illegal-memory.png)

1. `context.set_input_shape("input", (4, 3, 224, 224))`는 static engine이 받을 수 없는 shape이라 **`False`를 반환**하고 logger에 에러를 남깁니다. **예외는 발생하지 않습니다.**
2. context의 입력 shape은 그대로 `[8, 3, 224, 224]`입니다. 그래서 출력도 `(8, 1000)`입니다.
3. TensorRT는 넘겨받은 주소에서 **8장 분량(4.82MB)** 을 읽습니다. 입력 tensor는 4장(2.41MB)뿐이므로 뒤 절반은 **입력 버퍼 밖**입니다. 그 자리에 원본의 5~8번째 이미지가 있었기 때문에 `outputs[4][4:]`가 `outputs[8][4:]`와 정확히 같게 나왔습니다.
4. `execute_async_v3`도 `True`를 반환합니다. 실행 자체는 "성공"했습니다.

핵심은 **TensorRT가 버퍼의 주소만 받고 크기는 모른다**는 것입니다.
`set_tensor_address`에는 `data_ptr()`, 즉 GPU 메모리 주소 하나만 넘어가고, 그 주소에서 얼마나 읽을지는 engine이 알고 있는 shape이 정합니다.


### 1.2 왜 아무도 눈치채지 못하는가

위 실험에서는 `[TRT ERROR]` 줄이 셀에 찍혔지만, 이것은 실습 노트북이 TensorRT 메시지를 Python `print`로 출력하는 logger를 따로 만들어 썼기 때문입니다.
흔히 쓰는 기본 logger로는 상황이 다릅니다.

```python
logger = trt.Logger(trt.Logger.WARNING)
```

이 logger도 ERROR 메시지를 내보내기는 합니다. 하지만 Python 쪽이 아니라 **C++ 런타임의 stderr로 직접** 씁니다.

- **Jupyter / Colab**: C++ stderr는 셀 출력에 잡히지 않아서 화면에 아무것도 보이지 않습니다.
- **서버**: stderr를 따로 수집하지 않거나, 애플리케이션 로그와 다른 곳에 쌓이면 묻힙니다. 로그에 남더라도 코드는 멈추지 않고 다음 줄로 진행합니다.

호출한 코드 입장에서는 예외도 없고, `execute_async_v3`도 `True`이고, 정상처럼 보이는 `(8, 1000)` 출력이 돌아옵니다.
출력 개수가 입력과 다르다는 것 말고는 이상 신호가 없고, 그마저도 `outputs[:n]`처럼 앞부분만 잘라 쓰는 코드라면 드러나지 않습니다.

### 1.3 최악의 경우 ①: 프로세스가 죽는다

실험에서는 안전한 view를 썼지만, 실제 코드에서는 `data.imagenet_batch(4)`처럼 **독립된 tensor**가 들어옵니다.
이때 버퍼 밖에 무엇이 있는지는 아무도 모릅니다(out-of-bounds read, undefined behavior).

PyTorch는 GPU 메모리를 큰 덩어리(segment)로 받아 와서 그 안에 tensor를 나눠 배치합니다.
tensor가 segment 끝에 있어서 버퍼 바로 뒤가 할당되지 않은 영역이라면 다음 에러가 납니다.

```text
RuntimeError: CUDA error: an illegal memory access was encountered
```

이 에러는 해당 연산 하나로 끝나지 않습니다. CUDA context가 망가진 상태로 남아서, **그 프로세스의 이후 모든 CUDA 연산이 실패**합니다.

- 복구하려면 프로세스(노트북이면 커널)를 재시작해야 합니다.
- 드물게 GPU 자체가 응답하지 않는 상태가 되면 GPU reset이나 재부팅까지 필요합니다.
- 추론 서버라면 그 순간 처리 중이던 **모든 요청**이 함께 실패합니다. 잘못된 요청 하나가 서버 전체를 내립니다.

게다가 "batch 4가 들어오면 항상 죽는다"가 아니라 그때의 메모리 배치에 따라 죽기도 하고 안 죽기도 하므로, 재현하기도 어렵습니다.

### 1.4 최악의 경우 ②: 에러 없이 틀린 값을 반환한다

버퍼 뒤가 마침 할당된 메모리라면 crash는 나지 않습니다. 대부분이 이 경우입니다.
대신 다른 tensor의 데이터나 이미 해제된 메모리의 쓰레기 값을 입력으로 읽고, **그럴듯한 출력**을 돌려줍니다.
이쪽이 crash보다 더 위험합니다.

- 분류 모델이라면 존재하지 않는 이미지의 예측이 결과에 섞입니다.
- 얼굴 임베딩 모델이라면 엉뚱한 벡터가 나와서 **다른 사람으로 매칭**되거나 등록된 사람을 놓칩니다.
- 출력은 정상 범위의 숫자이므로 `NaN` 검사 같은 방어 코드에도 걸리지 않습니다.

로그도, 예외도 없이 시스템의 판단만 틀어지기 때문에, 문제가 드러나는 시점은 한참 뒤 결과를 사람이 확인할 때입니다.

출력 버퍼까지 생각하면 더 나빠질 수 있습니다.
위 코드는 출력 버퍼를 `context.get_tensor_shape("logits")`, 즉 engine의 shape `(8, 1000)`으로 만들었습니다.
만약 출력 버퍼를 **입력 batch에 맞춰** `(4, 1000)`으로 만들었다면, TensorRT는 8개 분량의 출력을 그 주소에 씁니다.
읽기가 아니라 **버퍼 밖에 쓰기**가 되어, 옆에 있던 다른 tensor(모델 가중치나 다른 요청의 데이터)를 덮어쓸 수 있습니다.

## 2. 입력 shape 검증: 명시적인 에러로 사고 막기

dynamic shapes를 지원하기 전에 먼저 할 일은, 이 **조용한 실패를 시끄러운 실패로 바꾸는 것**입니다.
지원하지 않는 shape이 들어오면 메모리를 건드리기 전에 예외를 던져서, 호출한 쪽이 바로 알 수 있게 합니다.

`context.set_input_shape`는 engine이 받을 수 없는 shape이면 `False`를 반환하므로, 이 반환값만 확인하면 됩니다.

```python
def trt_infer(context, x):
    x = x.contiguous()

    # engine이 허용하지 않는 shape이면 False를 반환한다 (예외를 던지지 않으므로 직접 확인)
    if not context.set_input_shape("input", tuple(x.shape)):
        raise ValueError(
            f"input shape {tuple(x.shape)}은 이 engine에서 실행할 수 없음 "
            f"(허용: {allowed_input_shape(context.engine)})"
        )

    # 출력 shape은 입력 shape이 정해진 뒤에 context에서 얻는다
    out = torch.empty(tuple(context.get_tensor_shape("logits")), dtype=x.dtype, device="cuda")

    context.set_tensor_address("input", x.data_ptr())
    context.set_tensor_address("logits", out.data_ptr())
    ok = context.execute_async_v3(torch.cuda.current_stream().cuda_stream)
    assert ok, "TensorRT 실행 실패"
    return out


def allowed_input_shape(engine):
    """에러 메시지용: engine이 받을 수 있는 입력 shape"""
    shape = tuple(engine.get_tensor_shape("input"))
    if -1 in shape:   # dynamic engine: 허용 범위는 optimization profile에 있다 (3장)
        mn, _, mx = engine.get_tensor_profile_shape("input", 0)
        return f"min {tuple(mn)} ~ max {tuple(mx)}"
    return str(shape)
```

같은 static engine에 다시 넣어 봅니다.

```python
for b in (8, 4):
    try:
        print(b, trt_infer(context, batches[b]).shape)
    except ValueError as e:
        print(b, "Error:", e)
```
결과:
```text
8 torch.Size([8, 1000])
4 Error: input shape (4, 3, 224, 224)은 이 engine에서 실행할 수 없음 (허용: (8, 3, 224, 224))
```

이제 batch 4는 실행 전에 막히고, 무엇이 왜 안 되는지 에러 메시지에 그대로 나옵니다.
logger 설정과 상관없이 Python 예외로 올라오므로 놓칠 일도 없습니다.

몇 가지 덧붙이면 다음과 같습니다.

- **출력 버퍼는 context가 알려주는 shape으로 만듭니다.** 입력 batch에서 출력 shape을 직접 계산하면, 1.4의 버퍼 밖 쓰기를 부를 수 있습니다.
- **dynamic engine에서도 필요합니다.** dynamic engine도 정해진 범위 밖의 shape은 똑같이 `False`를 반환하고 넘어갑니다(5장).
- **batch 축만이 아닙니다.** 해상도(`H, W`)나 채널 수가 다른 입력도 같은 방식으로 걸러집니다.

검증을 넣었다고 batch 4를 처리할 수 있게 된 것은 아닙니다. 사고만 막았을 뿐이고, 처리하려면 engine이 여러 shape을 받을 수 있어야 합니다.

## 3. dynamic shape을 만드는 두 단계

static engine은 빌드할 때의 shape 하나만 받습니다. 여러 batch를 받으려면 **두 군데**를 바꿔야 합니다.

```text
PyTorch ──export (① dynamic_shapes)──> ONNX [batch, 3, 224, 224]
        ──build  (② optimization profile)──> engine (batch 1 ~ 32)
```

### 3.1 ① ONNX export: batch 축을 동적으로 표시

이전 글의 export에 `dynamic_shapes` 하나만 추가합니다.

```python
from torch.export import Dim

DYN_MIN, DYN_OPT, DYN_MAX = 1, 8, 32

torch.onnx.export(
    model, (batches[8],), "resnet18_dynamic.onnx",
    input_names=["input"], output_names=["logits"],
    dynamic_shapes={"x": {0: Dim("batch_size", min=DYN_MIN, max=DYN_MAX)}},
    dynamo=True, external_data=False,
)
```

- **key는 `model.forward`의 인자 이름입니다.** torchvision ResNet의 `forward(self, x)`이므로 `"x"`입니다. ONNX 입력 이름(`"input"`)이 아닌 점에 주의합니다.
- **`{0: Dim(...)}`은 0번 축(batch)을 동적으로 둔다는 뜻입니다.** 나머지 축 `3, 224, 224`는 예제 입력의 값으로 고정됩니다.
- **출력의 batch 축은 자동으로 따라갑니다.** 출력 쪽에는 따로 지정하지 않아도 `logits`가 `[batch_size, 1000]`이 됩니다.

이렇게 만든 ONNX를 TensorRT로 parse하면 network 입력의 batch 축이 `-1`로 보입니다.

```text
network input : input (-1, 3, 224, 224)
```

> **참고: batch 외의 축도 dynamic으로 둘 수 있습니다**
>
> 이 글은 모델 입력의 Channel·Height·Width가 `3 × 224 × 224` 하나로 고정되어 있다고 가정하고, batch 축(0번)만 동적으로 두었습니다.
> 하지만 `dynamic_shapes`에는 다른 축도 지정할 수 있습니다. `[B, C, H, W]` 입력이라면 1번이 Channel, 2번이 Height, 3번이 Width입니다.
>
> ```python
> dynamic_shapes={"x": {
>     0: Dim("batch_size", min=1, max=32),
>     2: Dim("height", min=224, max=640),
>     3: Dim("width",  min=224, max=640),
> }}
> ```
>
> 이 경우 optimization profile의 `min`/`opt`/`max`에도 batch와 함께 해당 축의 범위를 넣습니다(예: `min=(1, 3, 224, 224)`, `opt=(8, 3, 480, 640)`, `max=(32, 3, 640, 640)`).
>
> 모델이 고정된 shape 하나가 아니라 여러 해상도나 채널 수를 받을 수 있다면, Channel·Height·Width도 dynamic shape으로 빌드하는 것을 고려해야 합니다.
> 예를 들어 원본 비율을 유지한 채 resize한 프레임을 그대로 넣는 검출 모델이 여기에 해당합니다.
> 이런 모델을 고정 해상도로 빌드하면, 해상도가 다른 입력마다 resize·padding을 따로 해야 하거나 engine을 해상도별로 여러 개 두어야 합니다.
>
> 다만 모델 구조가 그 축의 변화를 실제로 받아들일 수 있어야 합니다.
> ResNet은 마지막에 AdaptiveAvgPool이 있어서 Height·Width가 달라도 동작하지만, 첫 Conv의 가중치가 입력 채널 3개로 정해져 있으므로 Channel은 바꿀 수 없습니다.
> 또 batch 때와 마찬가지로 kernel은 `opt` shape 기준으로 선택되므로, 범위를 넓게 잡을수록 `opt`에서 먼 shape의 속도는 떨어질 수 있습니다.

### 3.2 ② optimization profile: 범위와 기준 shape 지정

ONNX가 "batch는 정해지지 않았다"고만 알려주면, TensorRT는 kernel을 고를 수 없습니다.
1편에서 봤듯 TensorRT는 빌드할 때 **실제 shape으로 후보 kernel을 돌려 보고** 가장 빠른 것을 고르는데, shape을 모르면 측정할 수가 없기 때문입니다.
그래서 빌드 config에 optimization profile로 shape의 범위를 알려줍니다.

| 값 | 의미 |
| --- | --- |
| `min` | 실행할 수 있는 가장 작은 shape |
| `opt` | kernel(tactic)을 고를 때 기준으로 삼는 shape. 이 shape에서 가장 빠르다 |
| `max` | 실행할 수 있는 가장 큰 shape. 중간 activation 메모리도 이 기준으로 잡는다 |

`min`~`max` 범위 안의 shape은 모두 실행할 수 있고, 범위 밖이면 `set_input_shape`가 `False`를 반환합니다.

두 단계는 짝이 맞아야 합니다.

- **ONNX만 dynamic이고 profile이 없으면** 빌드가 실패합니다. dynamix axis의 범위를 모르기 때문입니다.
- **ONNX가 static이면** profile을 줘도 범위를 바꿀 수 없습니다. ONNX에 고정된 축은 TensorRT에서도 고정입니다.

## 4. dynamic engine 빌드와 추론

### 4.1 빌드

이전 글의 `build_engine`과 비교하면, `# ── 추가 ──` 부분만 다릅니다.

```python
import tensorrt as trt

logger = trt.Logger(trt.Logger.WARNING)
builder = trt.Builder(logger)
network = builder.create_network()
parser = trt.OnnxParser(network, logger)
with open("resnet18_dynamic.onnx", "rb") as f:
    if not parser.parse(f.read()):
        for i in range(parser.num_errors):
            print(parser.get_error(i))
        raise RuntimeError("ONNX 파싱 실패")

config = builder.create_builder_config()
config.set_memory_pool_limit(trt.MemoryPoolType.WORKSPACE, 1 << 30)

# ── 추가: optimization profile ──
profile = builder.create_optimization_profile()
profile.set_shape(
    "input",                          # ONNX 입력 이름
    min=(DYN_MIN, 3, 224, 224),
    opt=(DYN_OPT, 3, 224, 224),
    max=(DYN_MAX, 3, 224, 224),
)
config.add_optimization_profile(profile)
# ────────────────────────────────

engine_bytes = builder.build_serialized_network(network, config)
if engine_bytes is None:
    raise RuntimeError("engine 빌드 실패")

with open(f"resnet18_dynamic_b{DYN_MIN}-{DYN_OPT}-{DYN_MAX}.engine", "wb") as f:
    f.write(engine_bytes)
```

engine 파일명에는 profile 범위를 넣어 두었습니다. 1편에서 GPU 아키텍처와 TensorRT 버전을 파일명에 넣은 것과 같은 이유로, 어떤 batch까지 받는 engine인지 파일명만 보고 알 수 있게 하기 위해서입니다.

### 4.2 로드와 허용 범위 확인

```python
runtime = trt.Runtime(logger)
with open("resnet18_dynamic_b1-8-32.engine", "rb") as f:
    dyn_engine = runtime.deserialize_cuda_engine(f.read())
dyn_context = dyn_engine.create_execution_context()

for name in ("input", "logits"):
    print(name, dyn_engine.get_tensor_shape(name))
print("profile 0:", dyn_engine.get_tensor_profile_shape("input", 0))
```

결과:
```text
input   (-1, 3, 224, 224)
logits  (-1, 1000)
profile 0: [(1, 3, 224, 224), (8, 3, 224, 224), (32, 3, 224, 224)]
```

engine의 shape에는 batch가 `-1`로만 보이고, 실제로 받을 수 있는 범위는 `get_tensor_profile_shape`로 확인합니다. 순서는 `[min, opt, max]`입니다.

### 4.3 추론: 출력 shape은 입력 shape을 정한 뒤에

추론 함수는 2장의 `trt_infer`를 그대로 씁니다. static engine에서는 `set_input_shape`가 사실상 검증 역할만 했지만, dynamic engine에서는 이 호출이 **실제로 context의 입력 shape을 정합니다.**

```text
set_input_shape("input", (3, 3, 224, 224))
  → context.get_tensor_shape("logits") == (3, 1000)
```

그래서 순서가 중요합니다.

1. `set_input_shape`로 이번 입력의 shape을 정한다.
2. 그다음 `context.get_tensor_shape("logits")`로 출력 shape을 얻어 버퍼를 만든다.

순서를 바꾸면 출력 shape에 `-1`이 남아 있거나 이전 호출의 shape이 나와서, 버퍼 크기가 맞지 않습니다.
`engine.get_tensor_shape`는 항상 `-1`이 들어간 shape을 돌려주므로, 출력 버퍼를 만들 때는 **engine이 아니라 context에** 물어봐야 합니다.

## 5. 결과

profile 범위 안의 batch 1·3·8·32와, 범위를 하나 넘는 batch 33을 넣어 봤습니다.
batch 1~32는 같은 입력을 PyTorch FP32 모델에 넣은 결과와 비교했습니다.

```python
images = data.imagenet_batch(DYN_MAX)   # 실제 사진 32장

for b in (1, 3, 8, 32):
    y_trt = trt_infer(dyn_context, images[:b])
    with torch.inference_mode():
        y_torch = model(images[:b])
    ...

oversized = torch.randn(DYN_MAX + 1, 3, 224, 224, device="cuda")   # 검증에서 막히므로 내용은 무관
trt_infer(dyn_context, oversized)
```

| batch | 출력 shape | max \|diff\| (vs PyTorch) | top-1 일치 |
| ---: | --- | ---: | ---: |
| 1 | (1, 1000) | 1.24e-05 | 100% |
| 3 | (3, 1000) | 1.05e-05 | 100% |
| 8 | (8, 1000) | 1.81e-05 | 100% |
| 32 | (32, 1000) | 3.34e-05 | 100% |
| 33 | `ValueError` | - | - |

```text
ValueError: input shape (33, 3, 224, 224)은 이 engine에서 실행할 수 없음
            (허용: min (1, 3, 224, 224) ~ max (32, 3, 224, 224))
```

- **모든 batch에서 출력 shape이 입력과 같습니다.** static engine처럼 8개가 고정으로 나오지 않습니다.
- **정확도는 FP32 static engine과 같은 수준입니다.** 이전 글의 TensorRT FP32처럼 상대적으로 `1e-5` 수준의 미세한 차이만 있습니다.
- **범위 밖 batch 33은 2장의 검증에서 막힙니다.** TensorRT 로그에도 `does not satisfy any optimization profiles. Valid range for profile 0: [1,3,224,224]..[32,3,224,224]`가 남습니다.

Intro의 상황에 대입하면, **마지막에 남은 3장**과 **단일 이미지 1장**을 padding 없이 같은 engine으로 처리할 수 있게 되었습니다.

## 6. 운영 시 고려할 점

### 6.1 `opt`는 가장 자주 쓰는 batch로

TensorRT는 `opt` shape을 기준으로 kernel을 고릅니다.
범위 안의 다른 batch도 실행은 되지만, 그 shape에서 측정해 고른 kernel이 아니므로 최적이 아닐 수 있습니다.
같은 batch라도 그 shape 하나에 맞춰 빌드한 static engine보다 약간 느릴 수 있습니다.

그래서 `opt`는 범위의 중간값이 아니라 **실제로 가장 자주 들어오는 batch**로 둡니다.
대부분의 입력이 batch 8로 들어오고 가끔 나머지가 생기는 구조라면 `opt=8`이 맞고, 요청 하나씩 처리하는 실시간 서비스라면 `opt=1`에 가깝게 둡니다.

### 6.2 `max`는 필요한 만큼만, 넘는 입력은 나눠서

`max`를 크게 잡으면 받을 수 있는 범위는 넓어지지만, TensorRT는 중간 activation 메모리를 `max` shape 기준으로 잡습니다.
쓰지도 않을 batch 256을 위해 GPU 메모리를 미리 잡아 둘 필요는 없으므로, `max`는 실제로 필요한 크기로 둡니다.

`max`를 넘는 입력은 2장의 검증에서 에러가 나므로, 호출하는 쪽에서 `max` 이하로 나눠 넣습니다.

```python
def trt_infer_chunked(context, x, max_batch=DYN_MAX):
    return torch.cat([trt_infer(context, chunk) for chunk in x.split(max_batch)])
```

### 6.3 batch 크기 분포가 넓다면 profile을 여러 개

batch 1 근처와 batch 32 근처가 모두 자주 들어온다면, `opt` 하나로는 양쪽을 다 맞추기 어렵습니다.
이때는 engine 하나에 optimization profile을 여러 개(예: `1~4, opt 1` / `5~32, opt 16`) 넣을 수 있습니다.
profile마다 kernel이 따로 선택되고, 실행할 때는 context별로 어떤 profile을 쓸지 고릅니다.
가중치는 engine 하나에 한 벌만 있으므로, batch마다 engine을 따로 두는 방법보다 메모리를 아낄 수 있습니다.

### 6.4 `Using default stream` 경고

실행 중 다음 경고가 보일 수 있습니다.

```text
[TRT WARNING] Using default stream in enqueueV3() may lead to performance issues due to additional
calls to cudaStreamSynchronize() by TensorRT to ensure correct synchronization.
Please use non-default stream instead.
```

PyTorch의 기본 stream에서 실행해서 TensorRT가 동기화를 추가로 한다는 **성능 경고**이고, 결과에는 영향이 없습니다.
없애려면 `torch.cuda.Stream()`으로 stream을 따로 만들어 그 위에서 실행합니다.

## 마치며

이 글의 흐름을 정리하면 다음과 같습니다.

- **static engine은 다른 shape을 받으면 조용히 실패합니다.** TensorRT는 버퍼의 주소만 받기 때문에, 입력이 작으면 버퍼 밖을 읽고 틀린 값을 돌려주거나 illegal memory access로 프로세스를 망가뜨립니다. 에러는 logger로만 나가서 놓치기 쉽습니다.
- **그래서 shape 검증이 먼저입니다.** `set_input_shape`의 반환값을 확인해 명시적인 예외로 바꾸면, 메모리를 건드리기 전에 사고를 막을 수 있습니다. static이든 dynamic이든 필요합니다.
- **dynamic engine은 두 단계로 만듭니다.** ONNX export에 `dynamic_shapes`, TensorRT build에 optimization profile(min/opt/max)을 주면 engine 하나로 범위 안의 batch를 모두 처리합니다.

static engine은 shape 하나에서 가장 빠르고, dynamic engine은 engine 하나로 범위 안의 shape을 처리합니다.
어느 쪽을 쓰든 **engine이 받을 수 있는 shape을 코드가 확인하는 것**은 빠뜨리면 안 됩니다.
